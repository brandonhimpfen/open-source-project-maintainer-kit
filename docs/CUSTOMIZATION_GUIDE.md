# Customization Guide

The files in this kit are templates. They should be reviewed and adapted before use.

## 1. Find placeholders

Search the entire kit for `[` and `]`. Replace placeholders such as:

- `[PROJECT NAME]`
- `[CONTACT METHOD]`
- `[PRIVATE SECURITY CONTACT OR REPORTING METHOD]`
- `[DOCUMENTATION LINK OR LOCATION]`
- `[SUPPORT CHANNEL]`

Some square brackets are Markdown checkboxes such as `- [ ]`. Do not replace those.

## 2. Decide which files you need

Not every repository needs every template. Remove files or sections that do not reflect how the project actually operates.

## 3. Make commitments realistic

Avoid publishing response-time promises, support commitments, security guarantees, or governance processes that the project cannot actually maintain.

## 4. Review security reporting

Use a genuinely private reporting channel for vulnerability reports. Do not instruct reporters to place sensitive vulnerability details in public issues.

## 5. Review licensing

The licence in `LICENSE.txt` governs this purchased template kit. It does not select a software licence for your open source project.

Choose your project's software licence separately and ensure that you have the rights needed for all code, documentation, media, and third-party material you distribute.

## 6. Review platform-specific metadata

The included GitHub issue and pull-request templates use common repository file locations. If you use another hosting platform, adapt their locations and metadata to that platform.

## 7. Final review

Before publishing:

- confirm all placeholders have been replaced;
- confirm names, links, contacts, and version information are accurate;
- remove instructions intended only for the template purchaser;
- check that the documents describe actual project practices; and
- obtain appropriate professional advice where your circumstances require it.
